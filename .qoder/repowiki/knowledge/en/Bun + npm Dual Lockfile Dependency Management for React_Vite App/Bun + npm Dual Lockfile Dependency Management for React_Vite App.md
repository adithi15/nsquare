## What system/approach is used

This repository manages JavaScript/TypeScript dependencies using **npm** as the declared manifest format (`package.json`) and **Bun** as the active lockfile resolver, producing a `bun.lock` file. A `package-lock.json` also exists alongside it, indicating that both npm and Bun have been used to resolve/install packages at some point. The project is marked `"private": true`, so it is not published to any registry.

There is no vendoring of third-party source code — all dependencies are resolved from the public npm registry (or configured registries) and installed into `node_modules` by the package manager.

## Key files and packages

- `package.json` — declares runtime and dev-time dependencies with caret (`^`) version ranges for most packages and a tilde (`~`) range for TypeScript (`~5.8.2`). It defines scripts for development (`dev`), build (`build`), preview (`preview`), cleanup (`clean`), and type-checking (`lint: tsc --noEmit`).
- `bun.lock` — the authoritative lockfile generated by Bun; it pins every transitive dependency to an exact version and includes SHA integrity hashes. It records the same dependency graph as `package.json` under its workspaces section.
- `package-lock.json` — npm's lockfile, present in the repo but superseded by `bun.lock` for resolution when using Bun.
- `tsconfig.json` — TypeScript configuration used by the `tsc --noEmit` lint script to enforce type constraints on dependencies.
- `vite.config.ts`, `tailwind.config.cjs` — build-tool configurations that pull in Vite plugins and Tailwind ecosystem packages declared in `package.json`.

Notable dependency groups:
- Runtime: React 19, React Router DOM v7, Express, Google GenAI SDK, Motion, Lucide icons, dotenv.
- Build/dev: Vite 6, `@vitejs/plugin-react`, TypeScript ~5.8, esbuild, tsx, Tailwind CSS v4 with `@tailwindcss/vite` plugin, Autoprefixer.

## Architecture and conventions

- **Single-package workspace**: There are no `workspaces` entries beyond the root entry in `bun.lock`; this is a flat single-project setup rather than a monorepo.
- **Version pinning strategy**: Most dependencies use caret ranges (`^`), allowing minor/patch updates within the major version. TypeScript is pinned more tightly with `~5.8.2`, suggesting a preference for patch-level stability on toolchain packages.
- **Lockfile-first reproducibility**: The presence of `bun.lock` means builds should be reproducible via `bun install` (or equivalent), which reads the lockfile instead of re-resolving semver ranges.
- **No private registry or scoped packages beyond standard npm scopes**: All packages referenced are from the default npm registry under standard scopes (`@google`, `@tailwindcss`, `@types`, `@vitejs`, etc.). No `.npmrc` or custom registry configuration was found in the inspected files.
- **Environment variables via dotenv**: The `dotenv` dependency indicates environment-driven configuration (e.g., API keys) loaded at runtime, complemented by a `.env.example` template file.

## Conventions and constraints

Observed conventions (descriptive):
- Dependencies are split between `dependencies` (runtime) and `devDependencies` (build/type/tooling) in `package.json`.
- Scripts encapsulate common tasks (`dev`, `build`, `preview`, `clean`, `lint`) so team members run the app consistently.
- TypeScript is enforced via `tsc --noEmit` in the `lint` script, catching type mismatches without emitting output.
- Both `bun.lock` and `package-lock.json` coexist; the lockfile in use depends on which package manager is invoked.

Constraints / enforcement observed:
- The project is private (`"private": true`), preventing accidental publication to npm.
- The `type: "module"` field enforces ESM module resolution across the project.
- The `scripts` field provides the only documented entry points for building and running the application.

No explicit policy was found governing how versions are updated (e.g., automated PRs, manual review gates), nor any vendoring or offline installation strategy beyond the lockfiles.
